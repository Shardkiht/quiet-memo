## 一、隐藏 bug

### B1 敏感信息正则误杀正常记忆（高）

位置：[`src/quiet_memo/memory/detect.py:9`](../src/quiet_memo/memory/detect.py#L9)

```python
SECRET_RE = re.compile(
    r"(api[_ -]?key|access[_ -]?token|secret|password|passwd|密码|口令|验证码|私钥)"
    r"\s*(是|为|[:：=])?\s*\S{4,}",
    re.I,
)
```

关键词后只要有 4 个以上非空白字符就命中，中文同样计入。实测（2026-10-27）：

| 输入 | 是否判为密钥 |
|---|---|
| 我的密码是 abc12345 | 是（正确） |
| API key: sk-xxxxx | 是（正确） |
| 密码忘记了怎么办 | **是（误判）** |
| 验证码一直收不到 | **是（误判）** |
| 这个软件的密码管理器好用 | **是（误判）** |
| secret 是 我心中的秘密 | **是（误判）** |

影响：命中后进入 `blocked` 而不是 `queued`（[`src/quiet_memo/memory/service.py:244`](../src/quiet_memo/memory/service.py#L244)），TUI 对话中不会提示；用户以为已经记住，实际什么都没写。

建议：把关键词后的“值”限制为 ASCII 凭据形态，例如 `[A-Za-z0-9_\-.:/]{4,}`；或要求关键词与值之间必须出现 `是/为/:/=` 之一，且值不含 CJK。补充“密码忘了/验证码收不到”类反例测试。

### B2 压缩前抽取失败 → 这批消息永久漏抽取（高）

位置：[`src/quiet_memo/agent/context.py:190`](../src/quiet_memo/agent/context.py#L190)

`_compact` 中 flush 失败只记录一条事件，随后仍然调用摘要器并追加 `summary` 记录（[`L208`](../src/quiet_memo/agent/context.py#L208)），该记录携带 `covered_records`。而后续沉淀游标以摘要边界为下界（[`src/quiet_memo/agent/session.py:141`](../src/quiet_memo/agent/session.py#L141)），因此被压缩掉的这批用户陈述此后不会再进入 `user_texts_after_distilled()`。

影响：LLM 抽取偶发失败（限流、超时）时，用户该轮陈述永久丢失，且没有任何重试入口。

建议：flush 失败时不要推进摘要覆盖边界，或把失败段落写入 `extraction_error` / 待补记队列，由启动补沉淀重试。

### B3 后台补沉淀队头阻塞（中高）

位置：[`src/quiet_memo/agent/runtime.py:297`](../src/quiet_memo/agent/runtime.py#L297)

```python
for session in self.sessions.unconsolidated(limit, exclude=exclude):   # limit=3
    ...
    if len(texts) < min_new_messages:   # 切换会话时 = 3
        continue
```

先取最近 3 个“需要沉淀”的会话，再判断新消息数量是否达标。如果这 3 个会话都只有 1–2 条新消息，它们会长期占住名额被跳过，更老的未沉淀会话永远进不了窗口。

建议：先按 `min_new_messages` 过滤再截断；或在跳过时顺延补足下一批。

### B4 会话切换后状态栏显示旧会话用量（中）

位置：[`src/quiet_memo/app/chat_app.py:463`](../src/quiet_memo/app/chat_app.py#L463)

- `AgentRuntime.start()`（[`runtime.py:70`](../src/quiet_memo/agent/runtime.py#L70)）与 `resume()`（[`runtime.py:85`](../src/quiet_memo/agent/runtime.py#L85)）都没有清空 `last_plan`。
- `_after_session_switch()` 直接调用 `update_status()`（[`chat_app.py:475`](../src/quiet_memo/app/chat_app.py#L475)），后者读取 `runtime.last_plan.estimated_tokens`。

影响：新建会话或恢复会话后，底部上下文进度条显示的是上一个会话的占用，直到发送下一条消息才纠正。`undo()` 反而清了 `last_plan`（[`runtime.py:389`](../src/quiet_memo/agent/runtime.py#L389)），行为不一致。

建议：`start()`/`resume()` 中重置 `last_plan = None`，或在切换后按新会话重新估算。

### B5 “改写后确认”产生多余 superseded 记录（中）

位置：[`src/quiet_memo/app/chat_commands.py:138`](../src/quiet_memo/app/chat_commands.py#L138)

```python
entry = self.service.approve(item_id)          # 先写原文
if override and override != entry.text:
    entry = self.service.correct(entry.id, override, reason="人工改写后写入")
```

影响：vault 里多出一条“从未被用户确认过”的原文（状态 superseded），audit 多两条记录；用户只看到改写后的版本。

建议：给 `approve` 增加可选 `text_override`，直接以改写文本写入，不产生中间条目。

### B6 记忆 Markdown 非原子写（中，推断）

位置：[`src/quiet_memo/memory/store.py:112`](../src/quiet_memo/memory/store.py#L112)

```python
path.write_text(f"---\n{front}\n---\n\n{body.lstrip()}", encoding="utf-8")
```

`write_text` 先截断再写入。TUI 后台补沉淀写 vault 时，前台检索可能读到空文件或半行，表现为某主题瞬时检索为空/少条目。注意 `vectors.npz` 与 `search-cache.json` 都已使用临时文件 + `os.replace`（[`vector.py:169`](../src/quiet_memo/retrieval/vector.py#L169)、[`cache.py:70`](../src/quiet_memo/infra/search/cache.py#L70)），只有 Markdown 没有。

建议：统一改为“写 `.tmp` 后 `os.replace`”，并在失败时清理临时文件。

### B7 向量后端失败后每次检索重试全量 embedding（中）

位置：[`src/quiet_memo/retrieval/vector.py:96`](../src/quiet_memo/retrieval/vector.py#L96)、[`L116`](../src/quiet_memo/retrieval/vector.py#L116)

异常时置 `_degraded = True`；`search()` 只要 `_degraded` 为真就重新 `sync()`。若 API Key 失效或额度耗尽，每个查询都会重新尝试嵌入所有未缓存条目。

影响：检索延迟持续升高、额度反复被打；用户只会感觉“搜索越来越慢”。

建议：degraded 状态加退避（例如 5 分钟内只重试一次），或直接降级 keyword 并在 `/status` 标注。

### B8 `/recall` 在 UI 线程同步检索（中）

位置：[`src/quiet_memo/app/chat_commands.py:68`](../src/quiet_memo/app/chat_commands.py#L68)

`/recall` 直接调用 `service.recall(...)`。hybrid 首次检索会触发 `VectorRetriever.sync()`（加载 fastembed 或调用 embedding API），在 TUI 事件线程中可能卡住数秒甚至更久。同类问题：`/model` 首次打开会在 UI 线程 import litellm、查询 keyring（[`actions.py:20`](../src/quiet_memo/app/actions.py#L20)）。

建议：`/recall` 走 `run_worker(..., thread=True)`，与 `_ask_work` 保持一致。

## 二、安全与合规

### S1 `fetch_web` 存在 SSRF 面（中）

位置：[`src/quiet_memo/agent/tools.py:486`](../src/quiet_memo/agent/tools.py#L486) → [`src/quiet_memo/infra/search/router.py:141`](../src/quiet_memo/infra/search/router.py#L141)

`fetch_web` 接受模型给出的任意 URL，本项目入口未校验协议与目标地址。模型可能被外部搜索结果中的提示注入诱导抓取 `http://127.0.0.1:...`、内网地址或云元数据地址（请求由本地 daemon 发出）。

补充核查（2026-10-28）：open-websearch 2.2.0 的 daemon 侧已实现 HTTP(S) 限制、私网/回环拒绝、代理模式下的逐跳 DNS 复验（`urlSafety.js`、`httpRequest.js`），因此这不是“已确认可利用的 SSRF”，而是本项目入口缺少纵深防护。修复仍按以下建议落地：

建议：
- 只允许 `http/https`；
- 解析后拒绝 `localhost`、回环、私网段、链路本地地址（含 `169.254.169.254`）；
- 对 `final_url` 做二次校验（防重定向绕过）。

### 已确认正常项

- 仓库内无真实 API Key；`quiet-memo.toml` 已被 `.gitignore` 忽略（`.gitignore:10`）。
- 密钥走 keyring/环境变量，`write_config` 不写 Key（[`providers.py:283`](../src/quiet_memo/infra/providers.py#L283)）。
- `evals/retrieval_eval.py` 为合成语料，不含真实个人信息。
- `read_topic` 只按主题名/标题匹配，不接受路径，无路径穿越。
- 会话 ID 有正则校验，`SessionStore._path` 拒绝非法 ID。
- 搜索缓存、向量缓存均在 vault 内并被 gitignore，属可重建派生数据。

### 小问题：TOML 未转义

[`src/quiet_memo/infra/providers.py:286`](../src/quiet_memo/infra/providers.py#L286) 将 vault 路径直接插进双引号字符串。路径含 `"` 时会生成非法 TOML。建议使用 `tomllib` 无法写回的前提下，至少对 `"` 和 `\` 做转义。

## 三、强耦合与架构

### A1 UI 直接读取 store

[`src/quiet_memo/app/chat_commands.py:175`](../src/quiet_memo/app/chat_commands.py#L175) `/topics` 使用 `self.service.store.entries(topic=...)`，绕过 `MemoryService` 的公开接口。建议 service 提供 `topic_entries(name)`，界面层不依赖存储实现。

### A2 同一批候选重复全量扫描

[`src/quiet_memo/memory/service.py:247`](../src/quiet_memo/memory/service.py#L247) 每个 candidate 调 `has_text()`（全库读一遍），[`L250`](../src/quiet_memo/memory/service.py#L250) 再调 `find_conflicts()`（再读一遍）。20 条候选 = 40 次全库读取。

建议：在一次 `_adjudicate` 内取一次 `entries()` 快照，增量维护“已写入”集合。

### A3 会话列表全量加载

[`src/quiet_memo/agent/session.py:218`](../src/quiet_memo/agent/session.py#L218) `list()` 逐个加载并解析全部会话文件；`refresh_sessions()` 在启动、每轮回复、后台提交后都会调用。启动补记也在 UI 线程先跑 `unconsolidated()`（[`chat_app.py:223`](../src/quiet_memo/app/chat_app.py#L223)）。

建议：缓存会话摘要（id/title/updated/count），只对变更文件失效；启动扫描移入 worker。

### A4 工具线程池不可强杀

[`src/quiet_memo/agent/tools.py:26`](../src/quiet_memo/agent/tools.py#L26) 全局 `ThreadPoolExecutor(max_workers=4)`；超时后 `future.cancel()` 只能取消未开始的任务。连续慢 `fetch_web` 会占满线程池，导致后续工具排队超时。建议为抓取类工具单独池，或改为可终止的子进程。

### 重复的指纹函数

[`src/quiet_memo/retrieval/keyword.py:52`](../src/quiet_memo/retrieval/keyword.py#L52) 与 [`src/quiet_memo/retrieval/vector.py:144`](../src/quiet_memo/retrieval/vector.py#L144) 各有一份 `_file_fingerprint`，逻辑完全一致。可下沉到 `MemoryStore`，避免存储格式变化时两处同时修改。

## 五、已确认良好的部分

- 分层依赖：`app → agent → memory → retrieval → infra`，未发现新增反向依赖或循环依赖。
- 忙碌态会话切换、新建会话、侧栏点击均会排队接续，不静默丢弃。
- 流式中断保留半截并显式标注；完成时就地定稿，不重复挂载。
- `undo` 通过追加事件实现，不重写 JSONL，且会让后续摘要失效。
- 敏感字段不写入配置；缓存文件均为派生数据且原子写。
- 测试夹具把 `QUIET_MEMO_CONFIG` / `QUIET_MEMO_VAULT` 钉在临时目录，且屏蔽 keyring 与真实 Key。
- CI 在 ubuntu-latest 与 windows-latest 双矩阵跑全量测试。

### 与原始建议的差异

- **B1**：原建议“值不含 CJK”会漏掉中文密码。实际规则改为：明确赋值（`是/为/:/=`）保留 Unicode，空白分隔只认 ASCII 凭据，无分隔只认 ASCII 可打印字符。`secret 是 我心中的秘密` 这类明确赋值仍保守拦截，已在 README 标注为启发式边界。
- **B2**：原建议“flush 失败不推进摘要边界”会导致压缩预算失效。改为把“摘要覆盖范围”和“已沉淀消息 ID”分开记录，两者都追加在 `summary` 事件中。
- **B7**：冷却时间取 60s（而非建议的 5 分钟），兼顾额度保护与恢复速度；`/status` 的检索模式仍由启动时构建结果决定。
- **S1**：上游 daemon 2.2.0 已有逐跳校验，本次是入口纵深防御，不宣称修复了可利用漏洞。
- **其他小项**：`_approve_locked` 已复查重复文本；`search_router` 的三元表达式已加括号，显式传入的 router 不再因 `enabled=false` 被丢弃。`Session.messages` 继续只统计用户消息，侧栏 “N msgs” 的产品语义未变。
